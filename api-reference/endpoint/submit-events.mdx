---
title: "Submit events"
description: "Submit user interaction events."
openapi: "/api-reference/openapi.json POST /v1/events"
---

Record an interaction or an array of up to 200 interactions. Use your application-owned `user_id`, the NSL integer `item_id`, and the non-zero integer event-type ID shown in **Data → Events**. Built-in event-type IDs can be negative.

```json
{
  "user_id": "user-123",
  "item_id": 3187,
  "event_id": 42,
  "context_id": 101,
  "request_id": "c7f0d2bb-56b1-4ca7-8f09-84d8e4ed02b4",
  "session_id": "visit-456"
}
```

## Attribution and retries

Copy `request_id` from the list the user acted on. Use `occurred_at` in Unix seconds for delayed or historical events. Reuse a `deduplication_id` only for retries of the same occurrence. Check the returned `inserted` and `processed` counts; additional diagnostic fields may be present.

## Search events

A search event has a non-empty `query` and no `item_id`. Its `event_id` can be omitted to use the workspace's Search signal binding. Include `result_item_ids` when your own search engine displayed results; those IDs do not count as clicked items.

Use [Search](/api-reference/endpoint/search) to record a search and fetch results in one call. See [Events](/integrate/events) for signal configuration, batching and delivery behaviour.
