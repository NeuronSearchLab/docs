## Why this exists

The SDK path asks you to render recommendations yourself and then send events back. That is two integrations, a backend to hold your credentials, and a mapping between your product ids and ours.

The embed collapses all of it. The widget that draws the recommendations is the widget that reports which ones were seen and clicked, so behavioural data arrives as a by-product of showing recommendations rather than as a prerequisite for getting any.

```html
<script src="https://cdn.neuronsearchlab.com/embed/1.2.0/nsl.min.js"
        data-nsl-key="nsl_pk_YOUR_KEY" async></script>

<div data-nsl-rec="related" data-nsl-item-url="auto" data-nsl-limit="6"></div>
```

That is the whole integration.

## Get a publishable key

<Steps>
  <Step title="Open Website embed">
    In the console, go to **Developers → Website embed**.
  </Step>
  <Step title="List your origins">
    Add every origin that will render the widget, including staging. A key with no origins does nothing.
  </Step>
  <Step title="Copy the snippet">
    The console gives you the script tag with your key already in it. The key is shown once, when you create it.
  </Step>
  <Step title="Check it is live">
    The same page shows the origins we have received requests from - including any we turned away because they were not on your list.
  </Step>
</Steps>

<Note>
  A publishable key (`nsl_pk_...`) is **designed to be readable** by anyone who views your page source. It can only read recommendations and report impressions - it can never administer your workspace, read your catalogue, or create credentials. This is not the same kind of secret as your Client Secret, and it is the only NeuronSearchLab credential that belongs in a browser.
</Note>

<Warning>
  **Never put a Client Secret or an `nsl_` secret key in browser code.** Those grant full access to your workspace. Publishable keys exist precisely so you never have to.
</Warning>

## Placeholders

| Attribute | Values | Notes |
| --- | --- | --- |
| `data-nsl-rec` | `related`, `feed` | Required. Anything else is ignored. |
| `data-nsl-item-url` | `auto` or a URL | `related` only. `auto` reads the page's `<link rel="canonical">`. |
| `data-nsl-limit` | 1-24 | Defaults to 6. |

`auto` is why no integration code is needed. Your catalogue is keyed on canonical URLs, so the page already knows which item it is - you never map your ids onto ours.

Placeholders added after load are picked up automatically, so single-page apps work without re-initialising anything.

## Styling

The strip renders in a shadow root, so your stylesheet cannot break it and it cannot leak styles into your page. CSS custom properties cross that boundary and are the supported way to restyle it:

```css
[data-nsl-rec] {
  --nsl-embed-font: "Inter", sans-serif;
  --nsl-embed-fg: #111;
  --nsl-embed-gap: 20px;
  --nsl-embed-radius: 12px;
  --nsl-embed-card-width: 200px;
  --nsl-embed-aspect: 3 / 4;
}
```

## Which URL to load

Subresource integrity and automatic updates cannot coexist on one URL, so both are offered rather than pretending otherwise.

| URL | Updates | `integrity` |
| --- | --- | --- |
| `/embed/<version>/nsl.min.js` | When you choose | Yes - **recommended** |
| `/embed/v1.js` | Automatic within v1 | No |

Per-version integrity hashes are published with each release.

## What it sends

- A recommendation request with the page's canonical URL and a random first-party visitor id. Your key travels as a header, never in the URL.
- **Impressions**, once a card has been at least 50% visible for two seconds. Scrolling past quickly is not an impression, and scrolling back does not double-count.
- **Clicks**, delivered with `sendBeacon` so they survive the navigation.

The widget never intercepts or delays a click. Your navigation happens exactly as it would without it.

No cookies, no third-party storage, no personal data. Visitor and session ids are random values in first-party `localStorage` and `sessionStorage`. Where storage is unavailable - private browsing, blocked site data - the widget still works and simply does not remember the visitor between pages.

## How the widget knows which item the page is

`data-nsl-item-url="auto"` reads the page's `<link rel="canonical">`, and the widget also reads the page's JSON-LD for a `sku`, `mpn`, `productID` or `isbn`. Both are sent, and whichever resolves against your catalogue wins - an identifier your feed asserted first, then one the crawler scraped, then the URL.

That second path matters more than it sounds. A canonical URL is only stable if the one a visitor's browser sees matches the one we crawled, and locale prefixes, per-market canonicalisation and AMP copies all break that. When they do, the strip used to quietly render unrelated items. Now the page's own `sku` resolves it, with no change to your markup.

You never need to send our ids. If you want to override what the page says, set `data-nsl-item-sku` or a literal `data-nsl-item-url`.

## When a strip is empty

Add `?nsl_debug=1` to any page carrying the widget. A panel appears listing every placeholder, what it resolved to, the request id, how many items came back, and how many events were sent - and names the cause when something is wrong:

- **Request failed** - the key is not valid for this origin. Check the origin list in the console.
- **This page is not in your catalogue** - the URL and sku matched nothing, so the strip is not related to anything.
- **No request_id** - the strip rendered but views and clicks are not being recorded.

`data-nsl-debug` on the script tag does the same thing permanently. The query parameter is usually what you want: the tag is typically baked into a theme, and it needs no deploy.

## Telling the widget what is happening

The crawl can see your product pages. It cannot see a basket, it does not know
whether anyone is signed in, and it never sees a thank-you page - those are
`noindex`, and correctly skipped. So the page may say, through a small command
queue:

```html
<script>window.nsl=window.nsl||function(){(nsl.q=nsl.q||[]).push(arguments)}</script>
<script src="https://cdn.neuronsearchlab.com/embed/1.2.0/nsl.min.js"
        data-nsl-key="nsl_pk_YOUR_KEY" async></script>

<script>
  nsl('page',     { type: 'product', item: { sku: 'AW-1042' } })
  nsl('cart',     { items: [{ sku: 'AW-9', quantity: 1 }], total: 98, currency: 'GBP' })
  nsl('customer', { id: 'cust-8821' })
</script>
```

| Command | Effect |
| --- | --- |
| `nsl('page', …)` | Which item this page is about. `type` is recorded for attribution and does not change ranking |
| `nsl('cart', …)` | What is in the basket. Nothing already in it is recommended, and on a page with no item of its own the basket seeds the strip |
| `nsl('page', { category })` | Scopes a listing page to its category |
| `nsl('page', { query })` | Turns a results page into query-driven retrieval |
| `nsl('customer', …)` | Who is signed in. Hashed per workspace; the raw id is never stored |
| `nsl('order', …)` | A completed sale. The only command that writes |
| `nsl('consent', false)` | Withhold cart and customer |
| `nsl('refresh')` | Re-read placeholders after a client-side navigation |

Commands **replace** rather than accumulate: calling `nsl('cart', …)` twice
describes one basket. You can mix them freely with JSON-LD - unlike a
tag-based integration, there is no mode to choose between.

If you cannot run script, one element does the same job:

```html
<script type="application/json" data-nsl-context>
  {"page":{"type":"product","item":{"sku":"AW-1042"}}}
</script>
```

<Note>
  Context resolves against your catalogue or it is dropped and counted. **It can never create an item.** That is what keeps a key published in page source from being a way to write to your catalogue.
</Note>

## Category and search pages

A listing page says what it is listing, and a results page says what was
searched:

```js
nsl('page', { type: 'category', category: 'footwear' })
nsl('page', { type: 'search',   query: 'running shoes' })
```

`category` filters on the `category` field of your item metadata. Catalogues
do not agree on what that field is called, so a value carrying its own field
wins - `topic:Health` filters on `topic`, a bare `Health` filters on
`category`.

`query` turns the request into query-driven retrieval. If the workspace has no
query embedder the request is retried without it, so the strip still renders
rather than leaving a hole in the page.

<Note>
  These scope a single strip from the page. To scope every strip on a surface, put the filter on the **context** the placement points at instead - one context can serve many placements.
</Note>

## Conversions

```js
nsl('order', {
  id: 'SO-1001',
  currency: 'GBP',
  items: [{ sku: 'AW-1042', quantity: 1, value: 49.99 }],
})
```

These arrive as **`purchase_reported`**, not `purchase`. A browser cannot prove
a sale happened, and `purchase` is the highest-weighted signal your models
train on, so the two are kept apart: `purchase_reported` is weighted 0 and
excluded from training, and exists for attribution and revenue reporting.

Order lines are keyed on the order id, so a reloaded thank-you page cannot
count a sale twice. If you also connect Shopify, the verified order **replaces**
the browser's report in place rather than adding to it.

An order id is required - without one there is nothing to deduplicate on.

## Placements

Give a strip a name, and what it serves becomes a console setting rather than a
markup change:

```html
<div data-nsl-rec="related" data-nsl-placement="pdp-related" data-nsl-item-url="auto"></div>
```

In **Developers → Website embed** a placement sets the context, the item count,
the layout (`grid` or `list`), which fields show, and an optional heading.
Per-placement click-through then appears without any extra instrumentation.

A placement the console does not recognise **still renders**, on your defaults.
Renaming one never blanks a live page.

---

## Events it will not send

The embed reports `view`, `click` and `purchase_reported` only.

`purchase` carries the highest weight in training and cannot be verified from a browser, so the API rejects it from a publishable key. Send conversions from your server with the [Events API](/api-reference/endpoint/submit-events), or import them with a [backfill](/guides/backfill).

Every event is also checked against the recommendations we actually served, so a key copied from your page source cannot be used to invent engagement for arbitrary items.

---

## Quota

Embed traffic is metered separately from API requests, because a recommendation strip makes one request per pageview.

When the allowance runs out the widget **keeps working** and serves cached results, with `X-NSL-Quota: exceeded` on the response. It does not start failing on your live site.

---

## Failure behaviour

Every failure path renders nothing and leaves the page untouched. The script sits in your critical render path, so it never throws, never blocks, and never shows an error to your visitors. It is under 4 kB gzipped.
