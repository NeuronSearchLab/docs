<Note>
  **On a shop platform?** Install the adapter instead — [Shopify](/embed/shopify), or [Magento, Shopware, PrestaShop and BigCommerce](/embed/platforms). The adapters send page, cart, customer and order context from what the platform already knows, so the manual steps on this page do not apply.
</Note>

The embed is a JavaScript widget you add to your site with a single script
tag. Wherever you put a placeholder element, it renders a strip of
recommendations drawn from your catalogue.

The same widget measures what it renders. Once a card has been on screen long
enough to have been seen, it records an impression; when a visitor clicks one,
it records that too. Those signals are what your models learn from, so
rendering and measurement arrive together rather than as two separate pieces
of work.

```html
<script src="https://cdn.neuronsearchlab.com/embed/1.2.0/nsl.min.js"
        data-nsl-key="nsl_pk_YOUR_KEY" async></script>

<div data-nsl-rec="related" data-nsl-item-url="auto" data-nsl-limit="6"></div>
```

Nothing else is required to render a strip. The sections below cover styling,
telling the widget about the basket and the customer, reporting sales, and
configuring what each strip serves from the console.

---

## Choosing between the embed and the SDK

Both serve the same recommendations from the same contexts.

| | Embed | SDK |
| --- | --- | --- |
| Renders the cards | Yes | You render them |
| Impressions and clicks | Recorded automatically | You send events |
| Credential | Publishable key, in the page | Client secret, on your server |
| Item identifiers | Resolved from the page | You map your ids to ours |
| Styling | CSS custom properties, or a console layout | Entirely yours |

The embed suits a website where you want recommendations rendered for you. The
SDK suits cases where you need full control of the markup, or where you are
serving somewhere a browser script cannot run — a mobile app, an email, a
server-rendered page you assemble yourself.

## Get a publishable key

<Steps>
  <Step title="Open Website embed">
    In the console, go to **Developers → Website embed**.
  </Step>
  <Step title="List your origins">
    Add every origin that will render the widget, including staging. A key with no origins does nothing.
  </Step>
  <Step title="Copy the snippet">
    The console gives you the script tag with your key already in it. The key is shown once, when you create it.
  </Step>
  <Step title="Check it is live">
    The same page shows the origins we have received requests from, including any we turned away because they were not on your list.
  </Step>
</Steps>

A publishable key (`nsl_pk_…`) is readable by anyone who views your page
source, and is built for that. Its permissions are limited to reading
recommendations and reporting impressions: it cannot administer your
workspace, read your catalogue, or create other credentials.

<Warning>
  **Never put a Client Secret or an `nsl_` secret key in browser code.** Those grant full access to your workspace. The publishable key is the only NeuronSearchLab credential intended for a browser.
</Warning>

## Placeholders

A placeholder is an empty element that marks where a strip should render.

| Attribute | Values | Notes |
| --- | --- | --- |
| `data-nsl-rec` | `related`, `feed` | Required. Anything else is ignored. |
| `data-nsl-item-url` | `auto` or a URL | `related` only. `auto` reads the page's `<link rel="canonical">`. |
| `data-nsl-limit` | 1-24 | Defaults to 6. |

`auto` is what removes the need for integration code: your catalogue is keyed
on canonical URLs, so the page already carries the identifier for the item it
is about.

Placeholders added to the DOM after load are picked up automatically, so
single-page applications work without re-initialising anything.

## Styling

The strip renders inside a shadow root. Your stylesheet cannot reach into it,
and its styles cannot leak out into your page. CSS custom properties cross
that boundary, and are how you restyle it:

```css
[data-nsl-rec] {
  --nsl-embed-font: "Inter", sans-serif;
  --nsl-embed-fg: #111;
  --nsl-embed-gap: 20px;
  --nsl-embed-radius: 12px;
  --nsl-embed-card-width: 200px;
  --nsl-embed-aspect: 3 / 4;
}
```

## Choosing a script URL

Two URLs are published. A versioned URL supports Subresource Integrity,
because its contents never change; a rolling URL updates itself, which is
incompatible with a fixed integrity hash.

| URL | Updates | `integrity` |
| --- | --- | --- |
| `/embed/<version>/nsl.min.js` | When you choose | Yes — **recommended** |
| `/embed/v1.js` | Automatic within v1 | No |

Per-version integrity hashes are published with each release.

## What the widget sends

- A recommendation request carrying the page's canonical URL and a random
  first-party visitor id. Your key travels as a header, never in the URL.
- **Impressions**, once a card has been at least 50% visible for two seconds.
  Scrolling past quickly is not an impression, and scrolling back does not
  count a second one.
- **Clicks**, delivered with `sendBeacon` so they survive the navigation. The
  widget does not intercept or delay the click itself.

It sets no cookies and uses no third-party storage. Visitor and session ids
are random values held in first-party `localStorage` and `sessionStorage`.
Where that storage is unavailable — private browsing, blocked site data — the
widget still renders and simply does not recognise the visitor on the next
page.

## How an item is resolved

A `related` strip needs to know which catalogue item the page is about. The
widget reads two things and sends both:

- the canonical URL, from `data-nsl-item-url="auto"`
- an identifier from the page's JSON-LD: `sku`, `mpn`, `productID` or `isbn`

Whichever resolves against your catalogue wins, in order of how much the
identifier is trusted: one your feed asserted, then one the crawler scraped,
then the URL.

Reading the identifier matters on sites where the canonical URL a visitor's
browser sees differs from the one we crawled — locale prefixes, per-market
canonicalisation and AMP copies all cause this. Where the URL does not match,
the page's own `sku` still resolves the item, with no change to your markup.

You never send NeuronSearchLab's identifiers. To override what the page says,
set `data-nsl-item-sku` or a literal `data-nsl-item-url`.

## Debugging an empty strip

Add `?nsl_debug=1` to any page carrying the widget. A panel lists every
placeholder, what it resolved to, the request id, how many items came back and
how many events were sent, and names the cause when something is wrong:

- **Request failed** — the key is not valid for this origin. Check the origin
  list in the console.
- **This page is not in your catalogue** — neither the URL nor the sku matched
  an item, so there is nothing for the strip to be related to.
- **No request_id** — the strip rendered, but views and clicks are not being
  recorded.

`data-nsl-debug` on the script tag enables the panel permanently. The query
parameter is usually more practical: the script tag is normally baked into a
theme, and the parameter needs no deploy.

## Page context

The crawler reads your product pages, but it cannot see a basket, it does not
know whether anyone is signed in, and it never reaches a thank-you page —
those are `noindex` and are skipped. Your page can supply that context through
a command queue:

```html
<script>window.nsl=window.nsl||function(){(nsl.q=nsl.q||[]).push(arguments)}</script>
<script src="https://cdn.neuronsearchlab.com/embed/1.2.0/nsl.min.js"
        data-nsl-key="nsl_pk_YOUR_KEY" async></script>

<script>
  nsl('page',     { type: 'product', item: { sku: 'AW-1042' } })
  nsl('cart',     { items: [{ sku: 'AW-9', quantity: 1 }], total: 98, currency: 'GBP' })
  nsl('customer', { id: 'cust-8821' })
</script>
```

| Command | Effect |
| --- | --- |
| `nsl('page', …)` | Which item this page is about. `type` is recorded for attribution and does not change ranking |
| `nsl('cart', …)` | What is in the basket. Its contents are excluded from results, and on a page with no item of its own the basket seeds the strip |
| `nsl('page', { category })` | Scopes a listing page to its category |
| `nsl('page', { query })` | Turns a results page into query-driven retrieval |
| `nsl('customer', …)` | Who is signed in. Hashed per workspace; the raw id is never stored |
| `nsl('order', …)` | A completed sale. The only command that writes |
| `nsl('consent', false)` | Withhold cart and customer |
| `nsl('refresh')` | Re-read placeholders after a client-side navigation |

Each command replaces the previous value for that slot rather than adding to
it, so calling `nsl('cart', …)` twice describes one basket. Commands and
JSON-LD can be mixed freely — there is no mode to select between them.

Where you cannot run script, one element does the same job:

```html
<script type="application/json" data-nsl-context>
  {"page":{"type":"product","item":{"sku":"AW-1042"}}}
</script>
```

<Note>
  Context resolves against your catalogue or it is dropped and counted. It can never create an item, which is what keeps a key published in page source from being a route into your catalogue.
</Note>

## Category and search pages

A listing page says what it is listing, and a results page says what was
searched:

```js
nsl('page', { type: 'category', category: 'footwear' })
nsl('page', { type: 'search',   query: 'running shoes' })
```

`category` filters on the `category` field of your item metadata. Catalogues
disagree about what that field is called, so a value may carry its own field
name: `topic:Health` filters on `topic`, while a bare `Health` filters on
`category`.

`query` turns the request into query-driven retrieval. If the workspace has no
query embedder, the request is retried without it, so the strip still renders.

<Note>
  These scope a single strip from the page. To scope every strip on a surface, put the filter on the **context** the placement points at — one context can serve many placements.
</Note>

## Conversions

```js
nsl('order', {
  id: 'SO-1001',
  currency: 'GBP',
  items: [{ sku: 'AW-1042', quantity: 1, value: 49.99 }],
})
```

Sales reported this way arrive as **`purchase_reported`**, a distinct event
from `purchase`. `purchase` is the highest-weighted signal your models train
on, and a browser cannot prove that a sale happened, so the two are kept
apart: `purchase_reported` is weighted 0, excluded from training, and used for
attribution and revenue reporting.

Order lines are keyed on the order id, so a reloaded thank-you page cannot
count a sale twice. An order id is therefore required — without one there is
nothing to deduplicate on.

If you also connect Shopify, the verified order replaces the browser's report
in place rather than adding a second record.

## Placements

A placement is a name you give a strip. What that strip serves then becomes a
console setting rather than a markup change:

```html
<div data-nsl-rec="related" data-nsl-placement="pdp-related" data-nsl-item-url="auto"></div>
```

In **Developers → Website embed**, a placement sets the context, the item
count, the layout (`grid` or `list`), which fields appear and an optional
heading. Click-through for each placement is then reported without further
instrumentation.

A placement the console does not recognise still renders, using your workspace
defaults, so renaming one does not blank a live page.

---

## Events the embed cannot send

The embed reports `view`, `click` and `purchase_reported`.

It cannot send `purchase`. That event carries the highest weight in training
and cannot be verified from a browser, so the API rejects it from a
publishable key. Send verified conversions from your server with the
[Events API](/api-reference/endpoint/submit-events), or import them with a
[backfill](/guides/backfill).

Every event is checked against the recommendations actually served, so a key
copied from your page source cannot be used to report engagement for arbitrary
items.

---

## Quota

Embed traffic is metered separately from API requests, because a strip makes
one request per pageview.

When the allowance is exhausted the widget continues to render, serving cached
results, and the response carries `X-NSL-Quota: exceeded`. It does not begin
failing on your live site.

---

## Failure behaviour

Every failure path renders nothing and leaves the page as it was. The script
sits in your critical render path, so it does not throw, does not block, and
does not surface errors to your visitors. It is under 4 kB gzipped.
