---
title: "Identity"
description: "Recognise returning visitors, link them when they sign in, and keep their history across devices."
---

NSL recommends for whoever sends the events. You choose the identifier, and the same person should keep the same identifier across visits and devices. There are three:

| Identifier | What it is | Lives |
| --- | --- | --- |
| `user_id` | Your own stable account ID | In your system. The only identifier that works across devices on its own. |
| `anonymous_id` | A random ID for a visitor who has not signed in | On the device: a first-party ID in the browser, or an install ID in an app |
| `session_id` | One visit | On the device, rotated after 30 minutes of inactivity by the SDKs |

No cookies are needed. NSL never uses third-party cookies, fingerprinting or advertising IDs.

## Anonymous visitors

Until someone signs in, send their anonymous ID as both `user_id` and `anonymous_id`. The JavaScript SDK (2.4.0 and later) creates one for you and uses it whenever you leave `userId` out. Swift support is coming; until then, generate a random install ID, store it, and send it yourself.

<CodeGroup>

```ts JavaScript
const sdk = new NeuronSDK({
  baseUrl: "https://api.neuronsearchlab.com/v1",
  tokenProvider,
  persistence: "localStorage", // remember the visitor across visits
  consent: false,              // until your consent banner says yes
});

// Later, from your consent platform
sdk.setConsent(true);

await sdk.trackEvent({ eventId: 42, itemId: 3187 }); // sent as the anonymous visitor
```

</CodeGroup>

In a browser, the anonymous ID is kept in first-party storage only when you enable persistence and consent has been given. Without consent the SDK keeps it in memory: recommendations still work for the current page, but the visitor is not recognised on their next visit. In the UK and EU, recognising a returning visitor for personalisation generally needs consent; use your existing consent platform rather than adding another banner.

The [website embed](/embed) manages its own anonymous ID and session. Pass your consent platform's decision with `nsl('consent', true | false)`.

## When a visitor signs in

Call `identify` with your user ID. The visitor's anonymous history moves onto that user, and from then on the SDK sends the user ID.

<CodeGroup>

```ts JavaScript
await sdk.identify("user-123");
```

```bash cURL
curl -X POST https://api.neuronsearchlab.com/v1/identify \
  -H "Authorization: Bearer <access_token>" \
  -H "Content-Type: application/json" \
  -d '{"anonymous_id": "aid_7f3c2b91e0", "user_id": "user-123"}'
```

</CodeGroup>

Each device links when the person signs in on it, so their laptop and phone history end up on one profile while their sessions stay separate. Two anonymous devices that never sign in stay two visitors: NSL does not guess that they are the same person.

See [Identify a visitor](/api-reference/endpoint/identify) for what moves and when a link is refused.

## When a visitor signs out

Call `reset()`. The SDK starts a new anonymous visitor and session, so the next person on a shared device is not linked to the previous one. An anonymous ID is only ever linked to the first user who signs in with it.

```ts
sdk.reset();
```

## Seeing it in the console

Open **Data → Users** and select a user. The **Identity** tab lists their devices, with the platform each one reported, whether it was linked at sign-in and how many earlier events moved, followed by their recent sessions. Each event on the **Events** tab shows the platform it came from.

## Erasure and export

Erasing a user removes their events, including those moved from anonymous IDs, and the links themselves. Links are included in the workspace export as `identity_links`.

## Identity resolution for partners

NSL Resolve is a separate, optional identity graph for partner workflows: matching hashed identifiers, recording consent purposes, minting partner-scoped IDs and data collaborations. It does not change recommendations; use `identify` for that.

## Resolve an identity

Call [Resolve identity](/api-reference/platform-api/identity/resolveIdentity) with a **Platform API key**, not a Core API access token. Send the identifiers you can verify and the consent decisions you have collected.

```bash
curl -X POST https://console.neuronsearchlab.com/api/identity/resolve   -H "Authorization: Bearer $NSL_API_KEY"   -H "Content-Type: application/json"   -d '{
    "identifiers": [
      {"type": "customer_user_id", "value": "customer-123"},
      {"type": "anonymous_id", "value": "visitor-456"}
    ],
    "consent": {"identity_resolution": true, "recommendations": true}
  }'
```

The response includes a canonical `identityId`, resolution status, confidence and consent information. Store that result in your application. If you use the canonical ID as your recommendation `user_id`, use it consistently for subsequent recommendations and events. Resolving identifiers alone is not a substitute for sending behaviour events or checking the purposes permitted by the response.

| Identifier family | Types |
| --- | --- |
| Customer and account | `customer_user_id`, `account_id`, `crm_id`, `subscription_id` |
| Anonymous and session | `anonymous_id`, `session_id`, `cookie_id`, `app_instance_id` |
| Contact hashes | `email_sha256`, `phone_sha256` |
| Device and household | `device_id`, `mobile_ad_id`, `ctv_device_id`, `household_id` |
| Partner | `external_partner_id` |

An identifier can also carry `namespace` and `source`. Keep namespaces stable when two systems could otherwise issue the same value to different people. For contact hash types, supply the expected normalized SHA-256 value rather than a raw address or number.

## Record and review consent

[Record consent](/api-reference/platform-api/identity/recordConsent) accepts `identityId`, a purpose-to-boolean `consent` map and an optional `source`. Purposes include `recommendations`, `personalisation`, `analytics`, `identity_resolution`, `cross_device_linking`, `measurement`, `third_party_activation` and `data_collaboration`.

Record changes when the user's choices change. Your application must also apply those choices to the data it sends and the features it enables; recording consent is not a blanket permission for every use of the identity.

In **Data → Users**, the **Identity** tab shows a user's resolved identity, consent and partner mappings below their devices, once they have one. Use [List consent records](/api-reference/platform-api/identity/listConsentRecords) for an API workflow.

## Partner-scoped IDs

Register a partner through [Create partner](/api-reference/platform-api/identity/createIdentityPartner), specifying its name, type and allowed purposes. Then [mint an NSL ID](/api-reference/platform-api/identity/mintNslId) for a resolved identity and that partner.

A partner-scoped NSL ID differs between partners. Use it when a partner needs a stable subject identifier without receiving your application's original identifiers. The canonical `identityId` is returned to your authorized application by the resolution API; a partner-scoped ID is a separate value. Minting requires the relevant activation or collaboration consent.

## Data collaborations

A collaboration lets two workspaces calculate aggregate overlap for approved identifiers.

1. [Create a collaboration](/api-reference/platform-api/identity/createDataCollaboration) with a partner workspace, allowed identifier types and optional expiry.
2. Have the other workspace [approve it](/api-reference/platform-api/identity/approveDataCollaboration).
3. [Contribute eligible identifiers](/api-reference/platform-api/identity/contributeDataCollaboration). Supported match types are `email_sha256` and `phone_sha256`.
4. [Calculate overlap](/api-reference/platform-api/identity/calculateDataCollaborationOverlap) and interpret the aggregate result.
5. [Revoke the collaboration](/api-reference/platform-api/identity/revokeDataCollaboration) when it is no longer needed.

Check approval, expiry and consent before contributing. The overlap result is a count-based comparison; it does not supply the other workspace's raw customer records.
